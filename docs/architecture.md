# Architecture: how this port is put together

## The runtime

The port does **not** emulate the Switch and does not translate the game's ARM64 code. The
title's own NSO modules (`rtld`, `main`, `subsdk0`, `sdk`) are mapped into a 39-bit guest
address space inside a normal Linux process, and:

- guest `svc` instructions are trapped by a host-side kernel layer that implements the Horizon
  services the title asks for (filesystem, storage, HID, audio, account, settings, …);
- NVN (the Switch graphics API) is recorded at the command-buffer level and replayed through
  EGL/GLES2 on the handheld's Mali GPU; shader programs are translated per stage;
- the RomFS is served from a single owner-supplied section file through the guest's own
  filesystem code.

The runtime is the recovered GPL baseline that also backs the West of Loathing port. The
recipe is the same: **baseline (verified by manifest) + this repo's adapter patch + an owner
image generated from the owner's own game copy**.

## The three inputs the build needs

1. **Recovered baseline source** — 435 files, pinned by `tools/baseline-manifest.sha256`.
   Reconstructed from the release's own `runtime-source.patch` / `nxgl-source.patch`.
2. **Owner image** — generated by `tools/prepare_lamentum_image.py` from the extracted game:
   - 12 segments (`rtld|main|subsdk0|sdk` × `text|rodata|data`) plus their bases, sizes and
     SHA-256 pins;
   - `image_table.h` with the title id, stack size, priority, core, allowed service list and
     the segment table;
   - `megaman_graphics_contract.h` with the NVN bootstrap/lookup identities derived from this
     title's `sdk` module (no borrowed offsets: the derivation follows the branch inside
     `nvnBootstrapLoaderInternal` and validates the four-instruction lookup thunk);
   - the RomFS section.
3. **Adapter patch** — `runtime/lamentum-adapter.patch`, currently 8 lines in two headers.

## What "bring-up" means here

The runtime fails closed. Every structure it does not recognise produces a named stop
(`STOP status=…`, exit code in the log) instead of a guess, and the GPL baseline is written
for a particular SDK generation. A new title therefore walks a frontier:

1. do the modules map, relocate and enter `rtld`? (no graphics involved)
2. does the guest reach Nintendo SDK initialisation and connect to its first services?
3. does it reach NVN (`nvnBootstrapLoader` → queue/device/memory-pool/buffer builders)?
4. does the recorded command stream replay, and do translated shaders produce content?

Each step answers with a stop code or a counter in the port log. The port's own status is
whatever the last run measured — not what the build was hoped to do.

## Panel path on this board

The runtime presents through SDL's KMSDRM backend, i.e. it owns the display while it runs; the
Spruce `MainUI` must be gone first (principal flow) or the two fight for the DRM master and
for ALSA. `fb0` is not the scanout, so any claim about the screen needs a DRM capture.
